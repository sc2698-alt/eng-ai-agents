1. DuckLake separates metadata from the actual data by storing schemas, snapshots, and table definitions in a SQL catalog while storing the data itself as Parquet files in object storage. This makes the system more scalable because large datasets can be stored efficiently without growing a single database file. It also enables features such as snapshot versioning, time travel, and rollback by creating new metadata rather than copying all of the data. 

    Now, for consistency implications, this means that for concurrent access, readers use a consistent snapshot while writers create new Parquet files and update the catalog. This allows multiple clients to read the data safely at the same time without interfering with one another. The tradeoff is that different users may temporarily see different snapshots until they refresh to the latest version.

2. In DuckLake, updates create new snapshots instead of modifying existing data files. When data changes, new Parquet files are written and the catalog records a new snapshot that references those files, while older snapshots continue to reference the previous versions. This allows the time travel queries to access the state of a table at an earlier snapshot, and rollback(s) can be performed by restoring a previous snapshot after an unwanted change. In this project, these features were demonstrated by creating snapshots, performing a schema change, querying an older version, and restoring the table after a bad update. The only real tradeoff in this is increased storage usage over time. Because older snapshots and their Parquet files are retained, they continue to consume storage until they are explicitly cleaned up.

3. Since DuckLake does not enforce primary keys or constraints, data quality had to be maintained during the transformation process. In the silver layer, the data was cleaned by correcting data types, handling missing values, and removing duplicate records before creating the transformed tables. The gold layer then selected only the columns needed for machine learning, which in turn produced consistent analysis ready datasets.

    Uniqueness in this case was therefore guaranteed by the ETL process rather than the database itself. By validating and cleaning the data during each transformation, the silver and gold tables contained reliable records even without the built-in database constraints.

4. When a row is inserted into a raw DuckLake table, DuckDB performs the write through the DuckLake catalog. The table metadata, schema, and snapshot information are stored in the DuckLake catalog file, `metadata.ducklake`. The actual table data is not stored inside that catalog file. Instead, DuckLake writes the new table contents as Parquet files into the RustFS object store.

    An example of this: when `raw.coco` was created from `/data/local/coco_raw.parquet`, DuckLake recorded the table and snapshot in the SQL catalog, then wrote a Parquet object under the RustFS `lakehouse` bucket, such as `raw/coco/...parquet`. The catalog knows which Parquet files belong to each snapshot, while RustFS stores the physical bytes. So the catalog stores the bookkeeping, and RustFS stores the data.

5. Storing the catalog in a SQL database makes metadata operations much simpler and more efficient. Table schemas, snapshots, version history, and time travel queries can be managed using standard SQL instead of scanning a bunch of metadata files. This provides fast metadata lookups and makes features such as snapshot comparison and rollback easy to implement.

    The tradeoff on this is that the catalog becomes a separate component that must remain synchronized with the Parquet files in object storage. If the catalog is lost or becomes inconsistent with the stored data, the tables cannot be reconstructed from the Parquet files alone as easily as with file only table formats.

6. The image and video files are stored as objects in RustFS rather than inside DuckLake tables because storing large binary files directly in a database would be extremely inefficient. Instead, the DuckLake tables store URI's and metadata describing each asset. For CoCo, the tables contain information such as image URI's, captions, labels, and dataset splits. For VisDrone, the tables store fragment metadata including frame ranges, object counts, and object classes.

    The VisDrone fragment index allows DuckDB to filter fragments using metadata, such as selecting fragments with a high number of detected objects, before accessing the corresponding files in RustFS. This avoids scanning entire video files and only materializes the fragments that satisfy the query, making the process extremely efficient.
